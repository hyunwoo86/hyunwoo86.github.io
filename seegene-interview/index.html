01 의료 자동화 시스템 설계
면접 답변 핵심

“검사별 상태를 등록·진행·완료·배출로 관리하고, 내부적으로는 분주·배양·촬영 단계를 작업 큐로 실행했습니다. 피펫이나 카메라처럼 공유하는 자원은 한 작업만 점유하도록 제어했습니다. 장애 후에는 DB 기록과 실제 장비 상태를 비교해 마지막으로 완료가 확인된 안전 지점부터 재개하고, 명령 ID와 완료 상태로 중복 분주나 촬영을 방지합니다.”

근거: 동시 검사 최대 16개, 명령당 최대 3회 시도, 시도당 60초
02 C#·.NET·WPF
면접 답변 핵심

“장비 통신과 영상 처리는 UI 스레드와 분리하고 async/await로 비동기 실행했습니다. 장시간 작업은 CancellationToken으로 안전하게 중단하며 예외는 로그와 상위 작업 상태에 전달합니다. 화면 변경만 Dispatcher에서 수행하고, 수신 데이터는 생산자-소비자 큐로 처리합니다. MVVM은 화면과 업무 로직 분리, DI와 Adapter는 실제 장비와 Emulator 교체, Repository는 상태 저장소 분리에 활용했습니다.”

03 TCP/IP 장비 통신
면접 답변 핵심

“TCP는 한 번의 수신이 한 메시지라는 보장이 없으므로 길이 정보나 구분자를 기준으로 버퍼에서 완전한 메시지를 조립합니다. 요청 ID로 응답을 연결하고 timeout·heartbeat로 통신 이상을 판단합니다. ACK는 명령 수신 확인일 뿐 실제 동작 완료와 구분합니다. 재연결 후에는 장비 상태를 다시 조회하고, 결과가 불명확한 동작은 자동 재전송보다 안전 정지를 우선합니다.”

04 DB·데이터 무결성
면접 답변 핵심

“검체, 검사, 단계, 장비 명령, 결과, 감사로그를 분리해 저장하고 검사 상태 변경과 명령 이력을 가능한 한 같은 트랜잭션 경계에서 관리합니다. 재실행 시에는 마지막 기록이 아니라 마지막으로 완료가 확인된 안전 지점을 기준으로 복구합니다. 검사 ID와 단계 ID를 중복 실행 방지 키로 사용하고 모든 자동·수동 변경을 audit trail에 남깁니다.”

05 Web Application 보완
면접 답변 핵심

“Web 제품 개발 경험은 없지만 C#/.NET 장비 SW에서 상태관리, 통신, DB, 권한과 오류 복구를 수행했습니다. Web 구조에서는 장비 통신 Worker와 업무 API를 분리하고, REST API로 조회·명령을 처리하며 실시간 상태는 SignalR로 전달하겠습니다. 인증·권한, 중복 요청 방지, 중앙 예외 처리, Swagger와 서버 로그를 기본으로 적용하겠습니다.”

작은 PoC 권장: 장비 Emulator → .NET Worker → DB → ASP.NET Core 상태 API
06 SW Validation
면접 답변 핵심

“Verification은 요구사항과 설계대로 만들었는지 확인하는 활동이고, Validation은 실제 사용 목적과 사용자 요구에 맞는지 확인하는 활동입니다. SRS·설계·구현·위험통제·시험을 식별자로 연결하고 정상뿐 아니라 경계·오류·복구 조건을 시험합니다. Emulator는 프로토콜과 흐름의 1차 검증에 사용하고 물리 동작과 성능은 실제 장비에서 확인합니다. 변경 후에는 영향받는 인터페이스와 위험을 기준으로 회귀시험을 선정합니다.”

07 PCR·검사실 자동화
면접 답변 핵심

“PCR 검사는 검체 접수와 바코드 확인, 핵산 추출, 반응액 준비, thermal cycling, 형광 측정과 Ct 분석, 결과 판정 순서로 이해하고 있습니다. 양성·음성·내부 대조군으로 검사 유효성을 확인하고 전처리와 증폭 구역을 분리해 오염을 관리합니다. 검체·시약 lot·장비·사용자·결과 변경 이력을 추적하고 LIS/LIMS에는 승인된 결과만 전달해야 합니다.”

08 사이버보안
면접 답변 핵심

“인증과 RBAC로 허가된 사용자만 검사 조건을 변경하게 하고, 실행 파일과 설정 무결성으로 변조를 탐지합니다. 외부 통신에는 TLS와 인증서를 적용하고 보안 이벤트는 감사로그로 남깁니다. SBOM/VEX와 취약점 평가로 알려진 위험을 관리하며 STRIDE에서 찾은 위협을 위험통제와 검증시험으로 연결합니다. 목표는 보안 자체가 아니라 검사 가용성, 결과 무결성과 환자 안전을 지키는 것입니다.”

“Web Application을 제품으로 개발한 실무 경험은 없습니다. 다만 C#/.NET 기반 장비 애플리케이션에서 장비 통신, 상태 관리, DB 저장과 복구, 사용자 권한, 오류 처리와 검증을 수행했습니다. Web에서는 실행 환경과 배포 구조가 달라지지만 핵심 비즈니스 로직과 데이터 무결성 문제는 연결된다고 생각합니다. 현재 ASP.NET Core Web API의 요청 처리, DI, 인증·권한, 실시간 상태 전달 구조를 중심으로 보완하고 있습니다.”
금지 표현: “WPF를 했으니 Web도 같습니다”, “금방 다 할 수 있습니다”, 실제로 만들지 않은 Web 프로젝트를 경험처럼 말하기

예상 기술 질문 12개

  1. dRAST에서 본인이 직접 설계·개발한 범위와 외주·AI팀의 범위를 구분해 주세요.
    답변 예시

    “저는 dRAST 3.0 Windows 애플리케이션의 UI와 검사 흐름, 작업 순서 관리, TCP 명령·응답 연동, 검사 상태 저장·복구, Emulator와 통합시험 도구를 담당했습니다. 장비를 직접 구동하는 하드웨어 미들웨어는 외주 개발 영역이었고, 영상분석 AI 프로그램은 별도 분석팀이 담당했습니다. 저는 두 시스템의 인터페이스와 오류 처리 조건을 협의하고 전체 검사 흐름 안에서 통합했습니다.”

    주의: 하드웨어 드라이버와 AI 분석 알고리즘까지 직접 개발했다고 확대하지 않기
  2. 검사 도중 프로그램이나 장비가 멈추면 어떤 상태를 저장하고 어디서 재개했습니까?
    답변 예시

    “검사 식별자와 현재 진행 상태, 완료된 단계 등 재개에 필요한 정보를 JSON과 SQLite에 저장했습니다. 재시작하면 저장된 상태만 믿고 즉시 다음 동작을 실행하지 않고, 장비가 실제로 어떤 상태인지 확인한 뒤 마지막으로 완료가 확인된 안전 지점부터 이어가도록 구성했습니다. 상태가 모호하면 자동 진행보다 사용자 확인과 안전 정지를 우선했습니다.”

    준비: 실제 저장 필드와 자동 재개가 가능한 단계·불가능한 단계를 본인 기억 기준으로 확정
  3. 동일 명령이 재전송될 때 중복 분주나 중복 촬영을 어떻게 막겠습니까?
    답변 예시

    “명령에 검사 ID와 단계 ID 같은 식별자를 부여하고, 명령 전송 전·응답 후 상태를 영속화하겠습니다. 타임아웃이 발생하면 무조건 재전송하지 않고 장비의 현재 상태나 완료 이력을 먼저 조회합니다. 결과를 확인할 수 없는 분주처럼 되돌리기 어려운 동작은 자동 재시도하지 않고 보류 상태로 전환해 운영자가 확인하도록 하겠습니다.”

    핵심어: 멱등성, 명령 식별자, 상태 조회, 모호한 결과는 안전 정지
  4. TCP 연결은 유지되지만 장비 응답이 늦는 상황을 어떻게 처리합니까?
    답변 예시

    “소켓 연결 상태와 장비 작업 상태를 분리해서 판단합니다. 요청별 타임아웃과 식별자를 두고, heartbeat나 상태 조회로 장비 생존 여부를 확인합니다. dRAST에서는 명령당 최대 3회 시도와 시도별 60초 제한을 두었습니다. 다만 실제 동작이 시작됐을 가능성이 있으면 즉시 재전송하지 않고 장비 상태를 확인한 뒤 재시도 여부를 결정합니다.”

    연결됨 = 정상 동작 중이라는 단순 판단을 하지 않기
  5. 여러 검체가 같은 모듈을 요구하면 스케줄링과 우선순위를 어떻게 정합니까?
    답변 예시

    “검체별 작업을 순서가 있는 큐로 관리하고, 모터·피펫·카메라처럼 동시에 사용할 수 없는 자원에는 예약과 잠금 정책을 적용합니다. 검사 안정성과 시간 제한을 우선하고, 같은 우선순위에서는 대기 순서를 따르되 장시간 대기하는 검체가 생기지 않도록 확인합니다. dRAST에는 여러 우선순위 정의가 있었지만 실제 운영에서 사용한 범위와 설계상 정의를 구분해서 설명하겠습니다.”

    실제 사용은 Normal·VeryLow 중심이었으며 7단계를 모두 운영했다고 말하지 않기
  6. Emulator에서 검증한 것과 실제 장비에서만 검증할 수 있는 것은 무엇입니까?
    답변 예시

    “Emulator에서는 명령·응답 프로토콜, 정상·오류 응답, 검사 순서와 UI 상태 전환을 빠르게 확인했습니다. 반면 실제 모터 동작, 액체 분주 정확도, 센서 편차, 온도 변화, 물리적 간섭과 실제 처리시간은 검증할 수 없습니다. 그래서 Emulator는 개발과 1차 회귀시험에 사용하고 최종 판단은 실제 장비 통합시험에서 수행했습니다.”

    Emulator가 장비 시험을 완전히 대체했다고 말하지 않기
  7. SRS 요구사항이 구현과 시험까지 추적되도록 어떤 산출물을 관리했습니까?
    답변 예시

    “dRAST에서는 테스트 항목에 Test ID와 SRS·SDDS 식별자를 연결해 요구사항과 설계, 시험의 관계를 추적했습니다. 현재 RayWatt에서는 SRS·SDS·위험관리 항목과 단위·통합·시스템 시험 결과를 연결하고, 합격 기준과 실제 결과가 확인되도록 V&V 문서를 보완했습니다. 변경 시에는 관련 요구사항과 위험통제, 시험 항목을 함께 확인합니다.”

    문서를 작성했다는 설명보다 변경 시 추적성을 어떻게 사용했는지 사례 준비
  8. 장애 수정 후 회귀시험 범위는 어떤 기준으로 선정합니까?
    답변 예시

    “변경된 요구사항과 모듈뿐 아니라 연결된 인터페이스, 공유 자원, 데이터 구조와 위험통제를 먼저 확인합니다. 그 결과로 직접 영향 시험과 주요 검사 흐름의 end-to-end 시험을 선정합니다. 환자 안전이나 결과 정확도에 영향을 줄 수 있는 기능은 변경 범위가 작더라도 실제 장비 시험을 포함하고, 영향이 없다고 제외한 항목도 근거를 남깁니다.”

    ‘전체를 다시 시험한다’보다 위험과 영향분석으로 범위를 설명
  9. Web Application 경험이 없는데 이 직무를 수행할 수 있는 근거는 무엇입니까?
    답변 예시

    “Web Application을 제품으로 개발한 실무 경험은 없습니다. 다만 C#/.NET 장비 애플리케이션에서 장비 통신, 상태 관리, DB 저장과 복구, 사용자 권한, 오류 처리와 검증을 수행했습니다. Web은 실행 환경과 배포 방식이 다르지만 핵심 업무 로직과 데이터 무결성 문제는 연결됩니다. 현재 ASP.NET Core Web API의 요청 처리, DI, 인증·권한과 실시간 상태 전달 구조를 중심으로 보완하고 있습니다.”

    WPF와 Web이 같다고 말하지 말고 공통 기반과 새로 배울 부분을 동시에 설명
  10. ASP.NET Core에서 장비 상태를 Web 화면에 실시간 전달한다면 어떻게 설계하겠습니까?
    답변 예시

    “Web 요청이 장비를 직접 제어하지 않도록 장비 통신을 담당하는 Worker와 업무 API를 분리하겠습니다. Worker가 장비 상태를 DB나 이벤트 채널에 기록하고, API는 현재 상태와 명령 요청을 관리합니다. 화면에는 SignalR로 상태 변경을 전달하되 재접속 시에는 DB의 최신 상태를 다시 조회합니다. 명령 API에는 인증·권한, 중복 요청 방지, audit log를 적용하겠습니다.”

    실무 경험이 아니라 준비한 설계안임을 명확히 하기
  11. PCR 검사 흐름과 dRAST 검사 흐름의 공통점과 차이점은 무엇입니까?
    답변 예시

    “둘 다 검체 식별, 분주, 시간·온도 제어, 장비 연동, 단계별 상태 관리와 결과 추적성이 필요한 IVD 자동화 시스템입니다. dRAST는 배양과 촬영·영상판독으로 항균제 감수성을 확인하지만, PCR은 핵산 추출과 반응액 준비, thermal cycling, 형광 신호와 Ct 분석이 핵심입니다. 따라서 자동화 SW 경험은 활용할 수 있지만 PCR 고유의 대조군과 오염방지 규칙은 별도로 학습해야 합니다.”

    ‘같은 IVD라 바로 할 수 있다’보다 공통 구조와 도메인 차이를 함께 인정
  12. 사이버보안 통제가 검사 결과 무결성이나 환자 안전과 어떻게 연결됩니까?
    답변 예시

    “권한이 없는 사용자가 검사 조건을 변경하거나 설정·바이너리가 변조되면 잘못된 결과나 장비 오동작으로 이어질 수 있습니다. 그래서 RBAC, 무결성 검증, TLS와 인증서, 감사로그를 단순 보안 기능이 아니라 위험통제로 봐야 합니다. SBOM과 취약점 평가로 알려진 위험을 관리하고, 각 통제가 실제로 동작하는지는 사전 합격 기준을 둔 시험으로 확인해야 합니다.”

    사이버보안 문서 작성보다 검사 가용성·결과 무결성·환자 안전 연결을 강조
